# Packaging

The Debian package and the apt archive that serves it.

## Layout

| Path | What it is |
| --- | --- |
| `debian/postinst` | Creates the service account, the project directory, and the systemd unit. |
| `debian/prerm` | Stops and disables the service on removal. |
| `debian/postrm` | Removes the generated unit; deliberately keeps the song library. |
| `debian/default` | Shipped as `/etc/default/mtrack`, a dpkg conffile. |
| `../scripts/build-apt-repo.sh` | Lays out and signs the archive. |

Package metadata (dependencies, description, assets) lives in
`[package.metadata.deb]` in `Cargo.toml`.

### The unit is generated, not shipped

`postinst` runs `mtrack systemd "$MTRACK_PATH"` against the binary it just
installed and writes the result to `/etc/systemd/system/mtrack.service`. There
is no copy of the unit in this directory, so `src/cli.rs` stays the only place
it is defined, and an upgrade re-renders it rather than leaving an operator on a
unit generated by a much older version.

An operator who edits the unit keeps their version. `postinst` stores an MD5 of
what it last wrote under `/var/lib/mtrack-packaging/`; if the file on disk no
longer matches, it is left alone and the upgrade prints the command to take the
packaged unit instead. The deployment guide tells people to add
`RequiresMountsFor=` by hand, so this is a case that will come up.

### Dependencies are hand-written

`depends` is set explicitly rather than using cargo-deb's `$auto`.
`dpkg-shlibdeps` emits *versioned* dependencies (`libasound2 (>= 1.0.16)`), and
`libasound2t64` — the time_t rename, from Debian trixie and Ubuntu noble onward
— only carries `Provides: libasound2 (= <version>)`. A versioned `Provides`
satisfies an unversioned `Depends` but not a versioned one, so an auto-generated
package builds cleanly on bookworm and then refuses to install on trixie. The
alternation `libasound2t64 | libasound2` resolves on both sides of the rename.

## Building a package locally

Packages are built from an already-built binary so the `.deb` and the release
tarball contain the same bytes:

```
$ cargo install cargo-deb
$ cargo build --release
$ cargo deb --no-build --no-strip
```

For another architecture, put the binary at
`target/<triple>/release/mtrack` and pass `--target <triple>`. Nothing executes
it, so one machine can build every architecture. `--no-strip` is required: the
host `strip` cannot process a foreign binary.

## Building an archive locally

```
$ sudo apt install apt-utils
$ ./scripts/build-apt-repo.sh --debs target/debian --out /tmp/repo
```

Unsigned, so apt needs `[trusted=yes]` to read it — fine for a smoke test,
never for anything published. Pass `--sign <keyid>` to sign it.

## Publishing: one-time setup

The `publish-apt` job in `.github/workflows/publish.yaml` is skipped until the
repository variable `APT_R2_BUCKET` is set, so the `.deb` on the release page
works without any of this.

### 1. Signing key

This is the part that is forever: the key is a trust root, it lives on every
installed device, and replacing it means every user editing files by hand.
Generate it offline, back up the secret key somewhere that is not GitHub, and
give it an expiry you are willing to renew.

```
$ gpg --quick-generate-key "mtrack archive signing <you@example.com>" ed25519 sign never
$ gpg --armor --export-secret-keys <fingerprint>   # -> secrets.APT_GPG_PRIVATE_KEY
$ gpg --armor --export <fingerprint> > mtrack-archive-keyring.asc
```

Publish the *public* key somewhere stable — it is what users install.

### 2. R2 bucket

Create a bucket and attach a **custom domain**. The `r2.dev` URL is rate
limited and documented as development-only, which is the wrong shape for
something every Pi hits on boot. Egress from R2 is free, so serving packages
costs storage only.

Create an API token scoped to that bucket (Object Read & Write).

### 3. GitHub configuration

Repository *variables*:

| Name | Value |
| --- | --- |
| `APT_R2_BUCKET` | bucket name |
| `APT_R2_ENDPOINT` | `https://<account-id>.r2.cloudflarestorage.com` |

Repository *secrets*:

| Name | Value |
| --- | --- |
| `APT_R2_ACCESS_KEY_ID` | R2 token access key |
| `APT_R2_SECRET_ACCESS_KEY` | R2 token secret |
| `APT_GPG_PRIVATE_KEY` | armoured secret key from step 1 |
| `APT_GPG_KEY_ID` | its fingerprint |

### 4. What users then run

Substituting the custom domain from step 2:

```
$ sudo mkdir -p /etc/apt/keyrings
$ curl -fsSL https://<your-domain>/mtrack-archive-keyring.asc \
    | sudo gpg --dearmor -o /etc/apt/keyrings/mtrack.gpg
$ sudo tee /etc/apt/sources.list.d/mtrack.sources <<'SOURCES'
Types: deb
URIs: https://<your-domain>
Suites: stable
Components: main
Signed-By: /etc/apt/keyrings/mtrack.gpg
SOURCES
$ sudo apt update && sudo apt install mtrack
```

## Notes on the archive

The pool is **cumulative**. `publish-apt` pulls the existing pool out of R2
before regenerating the indices, so every version ever published stays
installable and `apt install mtrack=0.16.0-1` works as a rollback. Nothing in
the pipeline deletes from `pool/`; only `dists/` is regenerated wholesale.

Packages are uploaded before indices. An index naming a `.deb` that is not in
the store yet is a hard failure for anyone running `apt upgrade` during the
window between the two syncs. The other order is merely briefly stale.

Only `arm64` and `amd64` are built, matching the release binaries. 32-bit
Raspberry Pi OS (`armhf`) is not covered.
